# 生产部署问题排查报告（2026-08-03）

## 结论

本次“服务器页面与本地不一致”和连续发布失败并非单一故障，而是三个部署问题叠加：

1. 发布工作流只上传镜像清单，没有同步当前版本的部署脚本和 Nginx 配置，服务器持续执行旧脚本。
2. 备份与维护容器改为非 root 用户后，已有持久化卷仍归 root 所有，导致写入失败。
3. Cloudflare 使用 HTTP 回源，但源站 Nginx 又将 HTTP 重定向到 HTTPS，形成无限重定向。

最终版本 `2026.08.03-prod5` 已完成发布，公网入口和全部核心容器均通过验收。

## 影响

- 旧发布可能显示 GitHub Actions 成功，但维护容器实际处于重启循环。
- 新发布第一次同步正确脚本后，备份卷权限问题被真实暴露并安全中止。
- 应用服务稳定后，公网首页仍因 Cloudflare 与源站协议配置冲突而重定向循环。
- 发布脚本在失败时保留了发布前备份，并尝试恢复上一版本；数据库未发生丢失。

## 根因与修复

### 1. 部署配置未随版本同步

**根因：** GitHub Actions 只把 `release.env` 上传到服务器，随后直接调用服务器目录中的旧版 `release.sh`。

**修复：**

- 每次发布生成白名单部署包。
- 上传部署包、版本清单及 SHA-256 校验文件。
- 服务器校验摘要后再解压部署脚本、Compose 和 Nginx 配置。
- 发布前保存服务器旧配置副本。

### 2. 非 root 容器无法写入旧卷

**根因：** 备份服务使用 UID `10002`，维护/API 服务使用 UID `10001`，但历史卷目录由 root 创建。

**修复：**

- 拉取新镜像后，先执行一次性卷属主迁移。
- 使用 `stat` 验证卷属主。
- 完成权限迁移后再创建发布前备份。
- 验收阶段检查维护目录可写、备份和维护状态有效。

### 3. 验收脚本解释器不匹配

**根因：** `acceptance.sh` 声明使用 `/bin/sh`，但包含 Bash 专属的 `[[ ... ]]`。

**修复：**

- 改为 POSIX `[` 条件语法。
- 新增 `check:shell`，禁止 `#!/bin/sh` 脚本使用 Bash 专属语法。

### 4. Cloudflare HTTPS 重定向循环

**根因：** Cloudflare 在边缘提供 HTTPS，但以 HTTP 访问源站；源站运行配置又返回 `301 https://...`，请求因此循环。

**修复：**

- 生产运行配置改用 `cloudflare-http.conf`，由 Cloudflare 负责公网 TLS。
- 自动检查要求运行配置与 Cloudflare 回源模板一致。
- 自动检查禁止 Cloudflare HTTP 回源配置再次加入源站 HTTPS 重定向。

## 新的发布保障

- 源码检查、72 项后端测试和前端生产构建。

- 失败时自动恢复上一版本应用镜像。

## 后续建议

1. 暂时保持 Cloudflare 负责公网 HTTPS 的现有模式。
2. 若以后希望使用 Cloudflare “完全（严格）”模式，应先在源站配置有效证书和 443 监听，再切换 Cloudflare，不能只改控制台选项。
3. 每次正式发布都通过 GitHub Actions 的 `release.yml` 执行，不再手工替换服务器文件。
4. 发布成功必须同时满足工作流成功、公网验收成功和服务器容器健康，不能只看镜像是否构建完成。
